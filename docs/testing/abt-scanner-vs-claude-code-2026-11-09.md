# 인터페이스 명세서: MonoField 스캐너와 일반 Claude Code 비교 (2026-11-09)

질문: 코드에서 인터페이스 명세서를 만들고, 코드가 바뀐 뒤 따라가는 일을 **MonoField의 결정적 스캐너·분류기**가 **일반 Claude Code**보다 잘하는가?

결론부터: 처음 잰 결과에서는 **정확도가 일반 Claude Code가 앞섰습니다.** MonoField가 앞선 것은 속도·비용·재현성이었습니다. 이 결과로 스캐너의 구체적인 버그를 찾아 같은 날 고쳤고, 고친 뒤 결과는 아래 [스캐너를 고친 뒤](#스캐너를-고친-뒤)에 있습니다. 이 문서의 표와 원인 분석은 **수정 전** 상태입니다.

## 실험 대상

실제 시스템이 아닌 **가상의 교통 ABT(계정 기반 승차권) 요금·결제·정산 플랫폼**입니다. 도메인 모델에서 Spring Boot 3.3.5 멀티모듈 코드를 생성했고 **실제로 컴파일됩니다**(v1·v2 모두 `mvn compile`).

| 항목 | 값 |
| --- | --- |
| 규모 | 모듈 8개, Java 213개 파일 8,119줄, REST API 68개(경로 68), DTO 107개, 열거형 17개 |
| 정답표 | 요청 필드 315, 응답 필드 573 (도메인 모델에서 계산, 코드를 읽어 만든 것이 아님) |
| 코드 스타일 혼합 | Lombok `@Data`/`@Getter`/`@Value`/`@Builder`, 직접 만든 getter/setter, Java `record`, 전자정부 VO(`*.do`, `Map` 응답), 제네릭 응답 래퍼(`ApiResponse<T>`, `PageResponse<T>`), 상속(`BaseResponse`), `@JsonProperty`·`@JsonIgnore`, 상수로 만든 경로(4개 컨트롤러), 추상 컨트롤러의 상속된 엔드포인트, 경로 별칭, 정규식 경로 변수, 멀티파트, 메서드 보안(`@PreAuthorize`), Java 보안 설정, XML 보안 설정 |
| 함정 | Feign 클라이언트(외부 호출이라 API가 아님), 테스트 소스의 가짜 컨트롤러, 주석 처리된 컨트롤러 코드, 어느 API에도 쓰이지 않는 DTO |
| 변경(한 번의 스프린트) | 29건, 33개 파일: A 18건(API 계약 변경), B 4건(열거값·기본값·권한 범위처럼 명세서 형식 밖), C 7건(내부 로직·리팩터링·주석·순서·내부 DTO·외부 호출·엔티티 속성처럼 **계약이 안 바뀌는 것**) |
| 변경 정답 | 159건: 일반 필드·API 변경 152, 경로·메서드가 바뀐 API 안의 필드 변경 3(필수 아님·감점 없음), 형식 밖 변경 4 |

공유 객체 변경이 여러 API로 퍼지는 경우(`Money.currency` 이름 변경이 116건, `OperatorRef`에 필수 필드 추가가 6건)를 일부러 넣었습니다.

## 비교한 것

| 팀 | 방식 |
| --- | --- |
| MonoField | `scan_spring.py`(결정적 스캐너)로 v1·v2를 각각 스캔하고, 제품에 들어 있는 `compareInterfaceSpecDocuments`로 호환성(깨짐/확인 필요/추가)을 분류. 모델 호출 없음 |
| 일반 Claude Code, 상세 지시문 | Sonnet. 출력 형식·래퍼·`@JsonIgnore`·상속·보안 설정 확인 방법까지 적은 지시문. 3회 |
| 일반 Claude Code, 짧은 지시문 | Sonnet. 출력 형식만 주고 함정 힌트는 없음. 3회 |

일반 Claude Code는 Read/Grep/Glob/Bash/Write 도구를 모두 쓸 수 있게 했고, 1단계(첫 명세서)와 2단계(변경 따라가기)를 **별도 세션**으로 돌렸습니다. 2단계에는 1단계에서 자기가 만든 명세서를 주었습니다.

### 영향받는 API 찾기 (MonoField의 `docs impact`, 증거 파일 기준)

변경된 33개 파일로 영향 API를 찾으면 58개를 표시했고, 실제로 바뀐 35개 중 34개가 그 안에 있습니다(재현율 97%). 나머지 24개는 같은 DTO 파일을 쓰지만 바뀐 필드를 쓰지 않는 API라 불필요한 표시입니다(정밀도 59%). 내부 로직·외부 호출처럼 계약이 안 바뀌는 변경은 표시하지 않았습니다.

### 재현성

- MonoField: 같은 코드를 3번 스캔한 결과의 해시가 모두 같습니다.
- 일반 Claude Code 상세 지시문: 1단계 결과가 3회 모두 정답표와 같았습니다. 짧은 지시문은 1회가 응답 필드 일부(약 4.5%)를 놓쳤습니다.

## MonoField 스캐너가 틀리는 원인

경로가 맞지 않는 API도 핸들러 이름으로 짝지어, 정답에 있는데 스캐너 출력에 없는 필드 190개와 정답에 없는데 있는 필드를 분류했습니다. 코드를 직접 읽어 확인한 원인만 적었습니다.

| 원인 | 확인 방법 | 영향 | 성격 |
| --- | --- | --- | --- |
| Java `record` DTO를 읽지 못함 | 클래스 정규식이 `class`만 인식(`dto_expander.py` `CLASS_RE`) | 응답 95 + 요청 38 필드 누락(가장 큼) | 미지원 |
| 상수·문자열 결합 경로를 풀지 못함 | 출력 경로가 `/ApiPaths.ACCOUNTS`로 나옴 | 23개 API의 경로가 틀림 → 변경 탐지 재현율 53% | 미지원 |
| `@JsonProperty` 이름을 반영하지 않음, 중첩 객체 안에서도 | 코드에 처리 없음. 출력은 Java 필드명 | 요청 6 + 응답 9 + 중첩 12 필드. 이름 변경(`fare_amount`→`fare`)도 놓침 | 미지원 |
| `@JsonIgnore` 필드를 포함 | 출력에 `riskScore`, `internalNote`가 있음 | 잘못된 필드 4개 | 미지원 |
| 헤더 파라미터를 못 읽고, `@RequestParam("from")`의 이름 대신 변수명을 씀 | `requestPayment`에 `Idempotency-Key` 없음, `listTrips`에 `fromDate` | 요청 7 필드 누락 + 오탐 | 미지원 |
| `Map` 응답의 `put` 키를 읽지 못함(전자정부 방식) | 해당 4개 API의 응답 필드가 비어 있음 | 응답 11 필드 | 미지원 |
| **감사 필드를 일부러 제외** (`createdAt`, `updatedAt`, `createdBy` 등과 이름에 `create`·`update`·`modify`·`reg`가 들어간 모든 필드) | `rules/audit_fields.py` | 상속받은 `BaseResponse`의 3개 필드와 `AutoChargeSettingResponse.updatedAt` 등 응답 10 필드 | **설계 의도**. 다만 규칙이 넓어 `registeredAt`처럼 업무 필드도 걸릴 수 있어 재검토 대상 |
| 필드 최대 길이 축소, 필수 헤더 추가를 변경으로 못 잡음 | 변경 정답 2건이 미탐지 | 변경 2건 | 형식 미지원 |
| XML 보안 설정을 읽지 않음 | 인증 "미정" 7건 | 인증 7건 | 제품 문서에 적힌 한계. **이후 고침**(아래) |

상속 필드(`extends`)와 `@ModelAttribute` 쿼리 객체는 정상 처리됩니다. 처음에는 상속을 원인으로 의심했지만 코드를 확인하니 아니었습니다.

위 원인 중 감사 필드를 뺀 전부를 고쳤습니다(회귀 시험 `scripts/tests/test_spring_modern_java.py` 11개 추가, 기존 36개 그대로 통과). 같은 가상 시스템과 같은 정답표로 다시 쟀습니다. 일반 Claude Code 열은 위와 같은 6회 결과입니다.

| 지표 | MonoField 수정 전 | MonoField 수정 후 | 일반 Claude Code |
| --- | --- | --- | --- |
| 첫 명세서: 경로 정확 | 62% | **100%** (68/68) | 100% |
| 요청 필드 재현율 / 정밀도 | 76% / 95% | **100% / 100%** | 100% / 100% (짧은 지시문 1회 제외) |
| 응답 필드 재현율 / 정밀도 | 69% / 92% | **98% / 100%**, 감사 필드 포함 옵션을 켜면 100% / 100% | 95~100% / 96~100% |
| 필수 여부 / 타입 정확도 | 94% / 97% | **100% / 100%** | 97~100% / 100% |
| 인증 판정 | 맞음 35, 미정 7 (42개 중) | **맞음 68, 틀림 0, 미정 0** (68개 중, XML 보안 설정을 읽은 뒤) | 68/68 |
| 변경 탐지 재현율 / 정밀도 | 53% / 61% | **100% / 100%** (152/152) | 96~100% / 100% |
| 호환성 분류·변경 종류 일치 | 100% / 100% | 100% / 100% | 94~100% / 99~100% |
| 열거값·기본값·권한 범위(형식 밖 4건) | 0/4 | 0/4 → **4/4** (2026-11-11, 아래 참고) | 4/4 |
| 영향 API 찾기 재현율 / 정밀도 | 97% / 59% | 파일 기준 97% / 57% → **코드 다시 읽기 100% / 100%** (34/34, 새 API 4개는 따로 표시) | — |
| 시간·비용 | 0.2초 · $0 | 스캔 0.3초, 영향 분석(다시 읽기) 0.7초 · $0 | 4~8분 · $1.0~1.4 |

고친 것(모두 코드와 시험으로 확인): **XML 보안 설정**(`<http>`, `<intercept-url>`, `security="none"`)을 Java 설정과 같은 모델로 판정하고 XML 파일과 줄을 근거로 남김, Java `record` DTO 읽기, 상수·결합 경로(`ApiPaths.V1 + "/x"`)와 컨트롤러 안의 상수 해석, `@JsonProperty`·`@JsonIgnore`·`@JsonNaming(SnakeCase)`, `@RequestHeader`와 `@PathVariable`·`@RequestParam`의 이름·필수 여부·타입(필수 여부는 Spring 기본대로 `required=false`·`defaultValue`가 없으면 필수), `Map` 응답의 `put` 키(컨트롤러 안, 그리고 서비스 구현을 따라간 경우), `@Size`·`@Length` 최대 길이 기록(길이를 줄이면 "깨짐"으로 분류됨), 감사 필드 규칙을 **낱말 단위**로 좁힘(`regDate`·`lastUpdatedBy`는 계속 제외, `registeredAt`·`region`·`registrationNo`는 유지) 및 `--include-audit-fields` 옵션 추가, `@GetMapping({"/a", "/b"})` 별칭 경로, 추상 컨트롤러가 가진 핸들러를 하위 컨트롤러 경로로 노출, 테스트 소스의 컨트롤러 제외.

감사 필드의 정확한 이름(`createdAt`, `updatedAt`, `createdBy` 등)은 여전히 기본으로 제외합니다(제품의 원래 설계). 필요하면 `--include-audit-fields`로 포함합니다. 기본값을 바꿀지는 별도 결정이 필요합니다.

### 영향 API 찾기를 코드 다시 읽기로 바꾼 뒤

처음 방식은 바뀐 파일을 근거로 쓴 API를 모두 표시했습니다. 공통 파일(`SecurityConfig.java`, 컨트롤러, 공유 DTO)이 바뀌면 그 파일을 쓰는 API가 다 걸려 60개를 표시했고 그중 26개는 실제로 바뀌지 않았습니다.

지금 `docs impact`(화면의 "영향 분석", CLI `monofield docs impact`, API `POST /api/projects/:id/documents/impact`)는 스캐너가 만든 명세서라면 **기준 커밋의 코드와 지금 코드를 같은 스캐너로 다시 읽어** 호출하는 쪽에서 보이는 차이만 비교합니다. 기준 코드는 임시 폴더에 꺼내 읽으며 사용자의 작업 폴더와 Git 인덱스는 건드리지 않습니다.

| | 파일 기준(이전) | 코드 다시 읽기(지금) |
| --- | --- | --- |
| 표시한 API | 60 | 34 |
| 그중 실제로 바뀐 것 | 34 | 34 |
| 불필요한 표시 | 26 | **0** |
| 놓친 것 | 문서에 없는 새 API 1 | **0** (새 API 4개를 "명세서에 없는 API"로 따로 표시) |
| 걸린 시간 | 0.04초 | 0.7초 |

다시 읽을 수 없으면(Python 3 없음, 스캐너가 만들지 않은 명세서, Git 저장소가 아님) 이전처럼 파일 기준으로 표시하고 그 이유를 화면과 CLI에 적습니다. 지금은 Spring 스캐너(`static-spring`)로 만든 명세서만 다시 읽습니다. 채점: `eval_all.py`의 `impact_rescan`.

### 열거값·기본값·권한 범위를 형식에 넣은 뒤 (2026-11-11)

명세서 형식에 필드의 허용값(`enumValues`)과 요청 기본값(`defaultValue`), API를 부를 수 있는 권한(`authorities`, 목록으로 줄일 수 없는 규칙은 `accessRule`)을 넣고 스캐너가 이를 읽게 했습니다. 같은 스프린트를 다시 돌린 결과입니다.

| 변경 | 보고 | 등급 |
| --- | --- | --- |
| B1 운수사 차단목록 증분 조회 권한 `SCOPE_blacklist.read` → `SCOPE_blacklist.admin` | API 1개 | 호환성 깨짐(정답과 같음) |
| B2 결제 상태(응답)에 `PARTIAL_REFUND` 추가 | 이 값을 돌려주는 API 3개 모두 | 확인 필요(정답과 같음) |
| B3 환불 사유(요청)에 `SYSTEM_ERROR` 추가 | 이 값을 받는 API 1개 | 추가 변경(정답과 같음) |
| B4 페이지 크기 기본값 20 → 50 | 페이지 조회 조건을 쓰는 API 8개 모두 | 확인 필요(정답과 같음) |

기존 변경 152건의 탐지(152/152, 오탐 0)와 첫 명세서 점수는 그대로입니다. 코드 다시 읽기 영향 분석은 38개를 표시했습니다. 34개는 기존 정답의 API이고 나머지 4개는 B1·B4만 바뀐 API라서 모두 실제로 바뀐 API입니다. 채점기는 두 쪽에 같은 기준을 쓰도록 고쳤습니다(형식 밖 변경 보고는 두 쪽 모두 오탐으로 세지 않음. 4건 탐지는 같은 낱말 판정으로 셈). 일반 Claude Code 쪽은 다시 돌리지 않았습니다.

### 수정 뒤에도 남은 것

- 한 API에 URL 규칙과 메서드 애너테이션이 둘 다 권한을 정하면 애너테이션의 권한만 적습니다(실제로는 둘 다 통과해야 함).
- 한 줄에 애너테이션과 메서드가 같이 있는 코드(`@PostMapping public R post(...)`), 중첩된 호출을 여러 단계 따라가야 키를 알 수 있는 `Map` 응답은 읽지 못합니다.
- 이 수정 이후의 일반 Claude Code 비교는 다시 돌리지 않았습니다(같은 열). 모델이나 코드가 달라지면 결과도 달라질 수 있습니다.

## MonoField가 실제로 앞선 것

- **속도와 비용:** 0.2초, 모델 비용 0. 일반 Claude Code는 한 주기에 4~8분, $1~1.4.
- **결정성:** 같은 입력이면 같은 출력. 자동 검사(CI)에서 "명세서가 코드와 어긋났는지"를 매번 같은 기준으로 판정할 수 있습니다.
- **호환성 분류 규칙:** 탐지된 변경의 분류가 100% 일치. 일반 Claude Code는 94~100%이고 실행마다 달라집니다.
- **코드가 PC 밖으로 나가지 않음:** 스캔과 비교에 외부 AI를 쓰지 않습니다. 외부 AI 사용이 제한된 SI·공공 현장에서 의미가 있습니다(이 실험으로 측정한 항목은 아니고 구조상의 사실입니다).
- **근거 위치와 영향 API:** 항목마다 파일과 줄이 남습니다. 영향 API는 기준 시점과 지금의 코드를 다시 읽어 비교해 찾으므로, 이 실험에서 실제로 바뀐 34개만 정확히 표시했습니다(오탐 0, 놓침 0).

## MonoField가 뒤진 것

- 첫 명세서 정확도: 수정 전에는 확실히 낮았고, 수정 뒤에는 이 가상 시스템에서 비슷해졌습니다(응답 필드는 감사 필드를 기본 제외해 98%). 이 결과는 생성한 코드 기준이라 실제 프로젝트에서는 다시 확인해야 합니다.
- 열거값·기본값·권한 범위 변경은 2026-11-09에는 못 찾았습니다. 2026-11-11에 형식과 스캐너를 고친 뒤로는 4건 모두 찾습니다.
- Spring(Java)만 고쳤습니다. Kotlin 컨트롤러는 읽지 않습니다.

## 이 실험으로 알 수 없는 것

- Excel·PPTX로 내보낸 **산출물 품질**, 검토 화면(UI)의 편의성, 변경 제안을 적용하는 흐름은 측정하지 않았습니다.
- 모델은 Sonnet 하나, 스프린트는 한 번, 시스템은 가상입니다. 생성한 코드는 실제 SI 코드보다 일관된 편이라 일반 AI에게 유리할 수 있습니다. 반대로 실제 코드는 더 길어서 토큰 한도·집중력 문제가 더 크게 나타날 수 있습니다.
- 정답표의 호환성 등급(`breaking`/`warning`/`info`)은 OpenAPI diff 도구의 관례를 따른 제 정의입니다. 등급 일치율은 이 정의에 따라 달라집니다.
- 채점기를 두 번 고쳤습니다(경로 정규화 불일치, 열거값·기본값 변경을 "정답에 없는 변경"으로 센 문제). 수정 뒤의 숫자만 위에 있고, 도구는 이 폴더에 그대로 있습니다.
- 처음 쓴 상세 지시문은 제가 심은 함정을 미리 알려 주는 편향이 있어 짧은 지시문 3회를 추가했고, 두 방식의 결과 차이는 작았습니다.
