# 변경 검증: 코드 작성 이후의 확인과 복구

MonoField의 역할은 연결한 Codex·Claude 등의 코드 작성 능력을 바꾸는 것이 아니라, 작성한 코드를 실행하고 확인하는 수고를 줄이는 것입니다. 개발 작업 공간의 **변경사항 → 변경 검증**에서 선택한 검사 명령을 실행하고 현재 코드에 대응하는 기록을 확인합니다.

## 사용 흐름

1. 개발 프로젝트에서 **변경사항**을 열고 **변경 검증**을 펼칩니다.
2. 실제 실행할 명령과 프로젝트에 정의된 스크립트를 확인합니다. 빠른 테스트·타입 검사·린트는 기본 선택하고 빌드는 직접 선택합니다. 자동 수정 옵션이나 명시적인 watch 명령은 기본 선택하지 않습니다.
3. **선택한 검사 실행**을 누릅니다. 검사별 종료 코드, 로그, 걸린 시간, 전체 실행 기록을 확인합니다. 검사당 제한은 UI에서 120초이며, 실행 중 중지할 수 있습니다.
4. 실패하면 **오류 수정 요청 작성**으로 실패한 명령과 제한된 실제 로그를 현재 채팅 입력란에 넣습니다. 내용을 검토하고 기존에 선택한 에이전트로 전송합니다. 자동 전송·모델 변경·추가 추론은 하지 않습니다.
5. 수정 후 같은 검사를 다시 실행합니다. 통과 기록은 검사 전후의 소스 지문이 같고 현재 소스와도 일치할 때 **선택한 검사 통과 · 현재 코드**가 됩니다.
6. 코드가 달라지면 **재검증 필요**가 됩니다. 에이전트가 작업하는 동안 이전 통과 표시를 해제하고, 작업 완료·앱의 파일 변경 알림·Git 변경 새로고침·검사 새로고침·화면 다시 열기·창으로 돌아오기를 계기로 결과를 확인합니다. 외부 변경을 항상 감시하는 기능은 아닙니다.
7. **검사 기록**에서 최근 10회 결과를 비교하고 **검사 기록 내보내기**로 JSON을 저장합니다. 내보낼 때 현재 소스 상태를 다시 확인합니다.

## 지원하는 명령

- Node 프로젝트의 `package.json`: `test`, `test:unit`, `typecheck`, `check:types`, `lint`, `build`.
- `packageManager` 또는 해당 모듈의 lockfile에 따라 npm·pnpm·yarn·bun을 사용합니다. 지정 정보가 없으면 npm입니다.
- `Cargo.toml`: `cargo test --locked`.
- `go.mod`: `go test ./...`.

설치된 도구와 의존성을 사용합니다. 의존성 설치나 모델 서버를 자동으로 시작하지 않습니다. 발견하지 못한 명령·Python·Java 등의 프로젝트는 기존 터미널을 사용합니다. 지원 범위를 전체 언어 지원이라고 표시하지 않습니다.

프로젝트 스크립트는 코드를 실행할 수 있습니다. 명령을 확인하고 실행하며, UI가 닫혀도 시작한 검사는 daemon에서 계속됩니다. 같은 Git 작업 트리에서는 한 번에 한 실행만 허용합니다. 서로 다른 작업 트리는 최대 두 개까지 실행하고, daemon의 정상 종료는 소유한 검사 프로세스를 중지합니다. Windows에서는 프로젝트 명령의 실제 실행 경로와 기존 플랫폼 명령 호출 경로를 사용합니다.

## 기록의 의미와 한계

검사 상태는 실제 프로세스의 종료 결과입니다. 실패·시간 초과·취소·daemon 종료로 미완료된 기록은 통과로 취급하지 않습니다. CLI의 `run --wait`도 검증 완료가 아니면 종료 코드 1을 반환합니다.

소스 지문은 Git HEAD와 작업 트리 전체의 추적 파일·무시되지 않은 새 파일의 경로, 모드, 내용에 대한 SHA-256입니다. 현재 모듈 밖의 공유 소스 변경도 재검증 대상으로 잡습니다. Git이 없는 폴더에서도 명령은 실행하지만 소스의 최신성은 미확인으로 남깁니다. 심볼릭 링크·서브모듈·20,000개 초과 파일·256 MiB 초과 소스·시간 제한 등으로 전체 지문을 확인하지 못하면 검증 완료로 표시하지 않습니다.

Git에 무시된 의존성·런타임 데이터·환경 변수·실제 DB의 내용은 지문에 포함하지 않습니다. 검사 전후와 현재 조회 시점의 지문을 비교하므로, 중간에 변경했다가 완전히 복원된 모든 순간까지 관찰하는 것은 아닙니다. `checkedAt`은 최신성 확인 시각입니다. 검사 통과는 선택한 명령의 결과이며 업무 기능 전체의 정확성을 보증하지 않습니다. 정답 품질은 해당 프로젝트의 의미 있는 테스트와 별도의 화면·API·DB 검증으로 확인해야 합니다.

검사별 출력은 마지막 32 KiB까지 보관합니다. 상속된 알려진 비밀 환경 변수와 Bearer 값은 마스킹하며, 모든 임의의 로그가 비밀정보를 포함하지 않는다고 보증하지는 않습니다. AI 수정 요청은 실패 로그만 검사당 최대 3,000자, 합계 최대 10,000자로 전달합니다. 로그를 진단 데이터로 표시하고 원래 의도를 보존하도록 요청합니다. 전달 전 입력란에서 확인할 수 있습니다. 원본 소스 내용과 자격증명은 검사 기록에 복사하지 않습니다.

기록 저장은 daemon의 활성 데이터 루트에서 파생하며 [데이터 경계](../AGENTS.md#daemon-data-directory-contract)를 따릅니다.

## CLI와 외부 에이전트

UI와 같은 HTTP API를 사용합니다. Codex를 계속 사용하는 개발자도 MonoField의 기록·실행 기능을 외부 에이전트에서 호출할 수 있습니다.

```bash
monofield verify plan --project <id> --json
monofield verify run --project <id> --checks node:test,node:typecheck --wait --json
monofield verify status --project <id> --json
monofield verify cancel --project <id> --run-id <receipt-id> --json
monofield verify repair --project <id> --run-id <receipt-id> --prompt-file <path|-> --json
monofield verify export --project <id> --run-id <receipt-id> --json
```

모듈은 `--project-path <relative-path>`, CLI의 명령별 제한은 `--timeout-ms <100..300000>`으로 지정합니다. `--wait` 없이 시작하면 실행 ID를 즉시 반환합니다. `export`는 최신성 상태와 해당 실행 기록을 stdout에 출력합니다. 실행 ID는 프로젝트와 모듈에 묶이며 다른 프로젝트의 기록을 조회하거나 중지할 수 없습니다.

API: `GET .../development/verification/plan`, `POST .../development/verification`, `GET .../development/verification?runId=...`, `POST .../development/verification/:runId/cancel`, `POST .../development/verification/:runId/repair`. 모두 기존 로컬 daemon 요청 권한 경계를 따릅니다.

## 선택 이유

모델 목록 추가·자동 모델 라우팅·Laya 자동 호출보다 이 기능을 먼저 선택했습니다. 지난 실측에서는 같은 개발 과제의 정답 품질 우위를 확인하지 못했고, 로컬 Laya만 약 1.8 GiB 메모리가 필요했습니다. 연결 수를 늘리거나 요청마다 판단 모델을 호출하는 것은 현재의 확인·복구 부담을 직접 줄이지 않습니다.

이 기능은 모델·외부 서비스·신규 패키지 의존성을 추가하지 않습니다. 검사 화면은 변경사항을 열었을 때만 지연 로딩하고, 펼치기 전에는 검사 탐색·실행·지문 수집을 하지 않습니다. 실행 중에만 결과를 조회하고 유휴 상태에서 주기적으로 전체 저장소를 읽지 않습니다. 검사 실패를 선택한 에이전트에 넘기기 전까지 AI 요청은 0회입니다.

차별점은 “코드를 더 잘 작성한다”가 아니라 **실제 결과가 어떤 소스에 대응하는지 남기고, 실패를 복구하는 흐름을 단축한다**는 것입니다. Codex 데스크톱보다 빠르거나 편하다는 비교 결과는 아직 없습니다. 터미널·CI만으로 이 흐름이 충분한 개발자에게 전환을 강요할 이유도 없습니다. 반복적으로 실행·검토·수정하는 사용자의 전체 완료 시간과 조작 횟수를 후속 실사용에서 비교해야 합니다.
