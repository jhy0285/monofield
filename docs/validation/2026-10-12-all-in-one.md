# MonoField 올인원 개발 실측 — 2026-10-12

## 결론

합성 Java/Spring + Vue 레거시 프로젝트에서 외부 IDE·브라우저 UI 없이 기능 구현, 개발 서버 실행, 화면 검증, Git diff, Java 터미널 디버깅, 문서 편집·출력을 완료했다. MonoField는 개발 결과를 화면·코드 근거·납품 문서로 연결하는 작업에 사용할 이유가 있다. 다만 Java 의미 기반 리팩토링·디버깅 GUI는 IntelliJ 수준이 아니며, 이번 동일 모델 비교에서 Codex CLI보다 빠르다는 결과도 나오지 않았다.

이 검증은 Linux 소스 실행을 대상으로 한다. 기존 Windows 설치본의 기능·성능, 실제 직원의 작업 시간, 며칠간의 안정성, 고객사 문서 승인까지 검증한 결과가 아니다. 최신 소스 수정이 설치본에 배포됐다는 뜻도 아니다.

## 수행한 개발 작업과 품질

기존 조회 기능에 신호 주기 수정과 변경 이력을 추가했다. 30–180 범위의 5 배수 정수만 허용하고, 소수·문자열·null 및 범위 위반은 400, 없는 ID는 404를 반환하도록 요청했다. Vue 화면에서 80 저장 성공과 31 입력 오류를 실제 브라우저 입력으로 확인했다.

양쪽 수정 코드에서 Maven 테스트 22개가 실패·오류·skip 없이 통과했다. Vue production build도 통과했다. 모델이 작성한 테스트와 별도로 실행한 HTTP 검사 19개는 기존 조회, 30/180 경계값, 감사 이력, 29/181/31/35.5/null/문자열 거절, 잘못된 요청의 비변경, 다른 교차로의 비변경을 확인했다. 서버 재시작 전후 값과 전체 이력도 같았다.

추가 요청은 서비스 메서드 `getSignalCycle(long)`를 `findSignalCycle(long)`로 바꾸는 것이었다. 양쪽에서 실제 서비스·컨트롤러·테스트 호출을 수정하고 Maven을 실행했다. 엔티티 getter와 BUSINESS.md의 같은 문자열은 유지했다. BUSINESS.md SHA-256은 양쪽 모두 `b91be687fce67cb7cfc169e8608ad5a3db4de1a09426d34bfa3b31acd33a80c7`이다.

이 결과는 지정한 기능의 검증이다. 보안·동시성·전체 제품 품질이나 모든 Java/Vue 프로젝트에 대한 보장은 아니다.

## 전체 프로세스 메모리

같은 Maven/Spring/Vite 서버가 준비된 상태에서 각 조합의 소유 프로세스와 자식을 `/proc`에서 약 1초마다 측정했다. MonoField 쪽에는 daemon/web·launcher wrapper·Electron guest·터미널 shell·Maven JVM·Spring JVM·Vite/esbuild를 포함했다. 공유 페이지를 배분한 PSS의 중앙값을 사용했다. 준비된 유휴 구간의 값이며 작업 중 최대 부하나 Windows 결과가 아니다.

## 조작 수와 실패 복구

기록된 X11 자동화는 click86, point-click45, key57, type33, paste6, focus4로 총231회다. 이 로그에는 onboarding, 오류 재현, 소스 수정 후 재확인, IntelliJ 설치/설정과 실험자 실수까지 섞여 있다. 일부 직접 도구 호출은 로그 밖에 있다. 두 경로가 같은 사용자 작업을 수행한 클릭 수 비교나 사람의 완료 시간으로 사용할 수 없다.

실제 관찰한 복구는 모듈 전환 후 재개 권한 실패, native PTY 설치 누락, 빠른 키 입력의 HTTP 순서 뒤바뀜, 이미지 경로 불일치였다. Java source classification도 직접 고쳤다. 브라우저 테스트의 창 focus/raise 누락과 IDE의 일시 정지 중 HTTP timeout은 실험 도구/조작 문제로 따로 남겼다.

## 이번 소스 수정과 검사

1. Java/Vue/XML/properties/Gradle 등 소스 분류와 text MIME을 확장하되 jar/class/db/실행 파일은 binary로 유지.
2. pnpm native build allowlist에 node-pty를 포함해 fresh source 설치에서 터미널 바인딩 생성.
3. terminal stdin HTTP 요청을 세션별 ACK 순서로 직렬화. 실패한 전송 뒤 대기 중 입력은 중단하고 부분 명령을 재전송하지 않음.
4. screen image export는 정규 project-relative 경로 우선, 기존 document-relative 경로 fallback. 프로젝트 경계 검사 유지.
5. Codex exec resume의 지원 config를 통해 기존에 명시적으로 허용한 writable roots를 전달. frontend 전환 뒤 backend 수정 성공을 실제 재측정.

관련 daemon 테스트102, web 테스트25가 통과했다. root guard(67 자체 검사), 전체 typecheck, web production build, daemon build도 통과했다. 이 결과를 저장소의 모든 기존 CI/전체 e2e 통과로 확장하지 않는다. 인증이 없는 벤더나 Windows 설치본은 이 작업에서 추가 검증하지 않았다.

## 반복 실행

저장소가 요구하는 Node/pnpm 버전을 쓰고 `pnpm install`을 먼저 실행한다. JDK 21 전체 개발 도구, Maven, npm을 PATH에 두고 JAVA_HOME을 설정한다. managed network의 프록시/CA는 유지한다. 실제 모델 요청에는 로그인과 비용/사용량이 필요하고 명시적인 `--run`을 넣어야 한다.

```bash
pnpm exec tsx e2e/scripts/all-in-one.ts prepare /tmp/mf-legacy
```

생성된 프로젝트에는 기존 조회 기능만 있다. 기준 Git commit을 만들고 각 lane에 별도 복사/checkout을 만든 뒤 Maven/npm dependency를 준비한다. 아래 경로는 별도 실험 workspace/output이며 daemon 데이터 저장 권장 경로가 아니다. 각 lane의 서버 포트를 독점 사용하고, 공유 CPU 실험은 순서대로 실행한다.

```bash
pnpm exec tsx e2e/scripts/all-in-one.ts direct /tmp/mf-direct /tmp/mf-direct-results feature --run
pnpm exec tsx e2e/scripts/all-in-one.ts direct /tmp/mf-direct /tmp/mf-direct-results refactor --run --active-module frontend --resume-result /tmp/mf-direct-results/feature.result.json
pnpm exec tsx e2e/scripts/all-in-one.ts monofield /tmp/mf-mono /tmp/mf-mono-results feature --run
pnpm exec tsx e2e/scripts/all-in-one.ts monofield /tmp/mf-mono /tmp/mf-mono-results refactor --run --resume-result /tmp/mf-mono-results/feature.result.json
```

MonoField 경로는 neutral tools-dev lifecycle로 isolated daemon을 열고 production API를 사용한다. 인증 파일을 복제하지 않고 CODEX_HOME을 이어 쓰며 종료 시 daemon을 중지한다. native UI는 따로 `pnpm tools-dev`로 열고 inspector screenshot과 실제 입력으로 확인해야 한다. 이 script가 native UI 전체를 자동으로 비교하는 것은 아니다.

```bash
pnpm exec tsx e2e/scripts/all-in-one.ts check http://127.0.0.1:8080 /tmp/mf-http-check.json
pnpm exec tsx e2e/scripts/all-in-one.ts sample /tmp/mf-memory.jsonl 12345,23456
```

`check`는 테스트 프로젝트의 신호 주기/이력을 실제로 변경한다. 운영 서비스에 실행하지 않는다. `sample`은 Linux 전용이며 PID roots를 실제로 확인해야 한다. 준비 시점·종료 시점을 따로 기록하고 SIGTERM으로 끝낸다. 서로 겹치는 root는 중복 집계하지 않고, 재부모화된 자식은 PID+startTicks로 추적한다. 읽지 못한 PSS는 incompletePss로 남긴다.

현재 출력 이름은 task 기반이므로 매 실험마다 새 output directory를 사용해야 이전 로그를 덮어쓰지 않는다. 반복 실험은 시간·캐시·프로세스 조건을 다시 기록한다.
