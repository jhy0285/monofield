# 변경 검증과 실제 오류 복구 — 2026-10-07

## 선택한 개선

이전 동일 과제 비교에서 MonoField의 일반적인 코딩 품질·속도·토큰 우위를 입증하지 못했다. 모델을 추가하는 대신, 개발자가 수정 결과를 확인하고 실패에서 복구하는 흐름을 구현했다. 기존 **변경사항** 화면에서 실제 프로젝트 명령, 종료 코드, 제한된 로그, 소스 지문, 최근 실행 기록을 확인하고 실패 로그로 현재 에이전트의 수정 요청 초안을 만든다.

검사 화면은 지연 로딩하고 펼치기 전에는 검사 API·소스 수집·모델 요청이 없다. 검사 실행도 사용자 동작으로만 시작한다. AI로 수정하기 위해 초안을 전송하는 기존 에이전트 요청에는 정상적인 공급자 사용량이 발생한다. 앱 전체의 메모리 사용량이 줄었다거나 Codex 데스크톱보다 빠르다는 비교 결과는 없다.

## 실제 네이티브 흐름

Linux Electron과 production web을 `tools-dev`의 격리된 런타임으로 실행했다. 실제 OS 폴더 선택과 X11 포인터로 의존성 없는 Node 청구 계산 모듈을 연결하고 버튼을 눌렀다. 이 수동 네이티브 검증은 API 응답을 가짜 성공으로 바꾸거나 직접 소스를 수정해 AI 성공으로 표시하지 않았다.

1. 원본 `amount * rate` 구현에서 의미 있는 두 테스트가 실패했다. 실제 `npm run test` 종료 코드는 1이었다.
2. **오류 수정 요청 작성**으로 실패한 명령·실제 로그가 기존 입력란에 들어갔다. 실제 **전송** 동작으로 로그인된 Codex에 요청했다.
3. 실제 에이전트 실행 `e2dc25d6-73e9-423a-9b60-6032bd5ff3af`가 성공했다. `billing.cjs` 한 줄을 `amount + amount * rate`로 바꿨고 테스트 파일은 바꾸지 않았다.
4. 같은 검사 버튼을 다시 눌러 두 테스트 통과·종료 코드 0을 확인했다. 검사 전후·현재 소스 지문이 일치하는 기록은 **선택한 검사 통과 · 현재 코드**로 표시됐다. 실제 수정 전후 diff도 함께 보였다.
5. 통과 후 소스에 진단용 주석을 추가하고 실제 **Git 새로고침**을 눌렀다. 이전 종료 코드 0 기록은 유지되면서 **재검증 필요**로 바뀌었다.

실패 기록은 `d344ca8e-3aed-4b32-b5c3-643993e0498e`, 수정 후 통과 기록은 `3f683608-2412-4653-b755-2f6501a5bcb6`이다. Codex 실행 시간은 23.433초였다. 공급자가 보고한 도구 루프 전체 사용량은 입력 95,984, 캐시 입력 83,072, 출력 453, 총 96,437이다. 캐시 입력은 입력에 포함된다. 이 요청을 직접 Codex 실행과 짝지어 비교하지 않았으므로 비용·속도 우위의 근거로 사용하지 않는다.

## 자동 검증

| 경계 | 결과 | 주요 확인 |
| --- | --- | --- |
| daemon 집중 회귀 | 29개 통과 | 실제 실패·수정·통과, 소스 변경, 실행 중 변경, 취소·제한 시간, 작업 트리 잠금, 재시작, 비밀 마스킹, HTTP 권한, CLI 종료 코드·내보내기 |
| web 집중 회귀 | 40개 통과 | 기본 접힘, 검사 선택, 수정 초안, 최신성, 모듈 변경, 에이전트 작업 중 통과 해제·완료 후 재확인, Git 화면, StrictMode 초기 탐색 |
| Playwright 실제 HTTP·UI | 1개 통과 | 프로젝트 연결, 실제 검사 실패, 초안 작성, 통과, JSON 다운로드, 변경 후 재검증 표시 |
| 저장소 검사 | 통과 | 전체 workspace typecheck, guard, production web·daemon build |

자동 Playwright 테스트에서는 fixture 소스를 테스트 도구가 직접 수정한다. 이 부분은 AI 성능 검증이 아니다. 위 실제 네이티브 Codex 요청과 구분한다. Linux 검증이며 새 Windows 설치본의 동작을 확인한 결과는 아니다.

CLI가 설정한 실패 종료 코드가 기존 공통 디스패처에서 0으로 덮이는 문제와 React StrictMode에서 취소된 개발 환경 초기 탐색을 재시도하지 않는 문제를 각각 실패하는 회귀 테스트로 확인한 뒤 수정했다. 소스가 변경된 경우와 소스 확인 자체가 불가능한 경우의 안내도 구분했다.

## 판단과 배포 범위

반복적으로 검사하고 실패 로그를 에이전트에 옮기는 개발자에게는 사용할 이유가 생겼다. 코드를 작성하는 지능은 연결한 Codex·Claude에 의존하며, 터미널·CI로 이 과정이 이미 편한 개발자에게 전환 이점을 입증한 것은 아니다. 실제 업무의 완료 시간·조작 횟수·복구 비용을 장기간 비교해야 한다.

이 변경은 개발 소스이며 공개 Windows v0.11.6 설치본을 갱신하지 않는다. 설치본 배포에는 새 버전의 Windows 빌드·설치·공개 피드 검증이 필요하다. 사용 방법과 지원 범위·소스 지문의 제한은 [변경 검증 안내](../change-verification.md)에 있다.
