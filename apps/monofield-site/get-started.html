GET STARTED · TECHNICAL GUIDE

10분 안에 따라 해 보는코드와 명세서 맞추기

MonoField가 하는 일을 설명만 하지 않고, 합성 주문·정산 앱 하나로 직접 돌려 봅니다. 브라우저에서 실제로 오간 요청·응답(REA 기록)을 인터페이스 명세서와 대조하고, 어긋난 곳을 고쳐 Excel로 내보내는 데까지 가며, 아래 출력은 모두 실제 CLI를 실행한 결과입니다.

준비

MonoField Windows Preview

설치본은 아직 코드 서명 전이라 Windows 보호 창이 뜰 수 있습니다. 설치 파일 받기

화면(UI)과 monofield CLI는 같은 로컬 데몬의 /api/* 를 호출합니다. CLI는 데몬이 떠 있어야 하며 --daemon-url 로 주소를 지정할 수 있습니다. 설치부터 첫 명세서까지의 전체 안내는 처음 시작하기(15분) 문서에 있습니다.

02

데모 프로젝트: 주문·정산

합성 주문·정산 앱입니다. 화면에서 주문 목록을 열고, 결제 완료 주문을 정산하고, 같은 주문을 다시 정산해 보고, 미결제·취소 주문을 정산해 보고, 정산 내역을 엽니다. REA가 이 장면을 Chromium에서 실행하며 오간 요청·응답을 기록한 파일이 증거입니다.

명세서에 있는 인터페이스

MethodPathID이름응답 필드
GET/api/ordersORDER-001주문 목록 조회7
POST/api/orders/{id}/settleORDER-002주문 정산 실행5
GET/api/settlementsSETTLEMENT-001정산 내역 조회6

REA가 기록한 API 호출 6건

POST/api/orders/1001/settle201
POST/api/orders/1001/settle409
POST/api/orders/1002/settle409
POST/api/orders/1003/settle409

프로젝트에 넣은 기록 파일 확인

$ monofield rea evidence --project <project-id>
evidence/capture.json  41.9 KB  2026-11-02T00:00:00.000Z

기록 파일은 REA 6.7.0의 capture_browser_scenario 결과이며 저장소의 apps/daemon/tests/fixtures/rea/ 에 있습니다. 본문마다 SHA-256이 들어 있어 MonoField는 일치할 때만 읽습니다.

명세서 파일(*.interface-spec.json)은 이렇게 생겼습니다 
{
  "kind": "interface-spec",
  "endpoints": [{
    "method": "POST",
    "path": "/api/orders/{id}/settle",
    "interfaceId": "ORDER-002",
    "interfaceName": "주문 정산 실행",
    "responseFields": [{
      "nameEn": "fee_amount",
      "nameKo": "수수료",
      "dataType": "Integer (observed)",
      "required": "TBD",
      "reviewStatus": "unreviewed",
      "evidenceRefs": [{
        "kind": "browser",
        "ref": "evidence/capture.json",
        "symbol": "ev_afc703c9…#request-4",
        "summary": "POST /api/orders/1001/settle → 201"
      }]
    }]
  }]
}

모든 행에 근거(evidenceRefs)와 검토 상태(reviewStatus)가 붙습니다. 관찰로 알 수 없는 필수 여부는 TBD로 남습니다.

04

구조 한눈에

Codex · Claude Code코드를 읽고 고치는 에이전트
MonoField daemon로컬 · /api/* · SQLite · 프로젝트 파일
UI · monofield CLI같은 API를 호출
REAMonoField 내장 · 브라우저·정적·DB 근거 수집
evidence/*.json프로젝트 폴더의 기록 파일
Laya · JEV선택: 로컬 판단 모델
  • 모든 기능은 UI와 CLI 두 길로 열려 있고, 둘 다 같은 데몬 API를 거칩니다.
  • MonoField는 파일을 임의로 바꾸지 않습니다. 화면은 변경을 편집기에 올려 사람이 저장하게 하고, CLI는 --write 를 줄 때만 쓰며 검토한 파일의 해시가 바뀌었으면 거부합니다.
  • 판단 모델이 없어도 규칙(빈 값, 번역 안 된 이름)은 동작합니다. 모델은 관찰 모드로 시작해 결과가 쌓인 뒤에만 플래그를 켭니다.

05

명령과 API 참조

CLI설명
monofield rea status|enable|disable대화에서 AI가 내장 REA를 쓸지 설정(기본 켜짐)
monofield rea evidence --project <id>프로젝트의 REA 브라우저 기록 파일 목록
monofield rea cross-check --project <id> --evidence <file>… [--input <spec>]기록과 명세서 비교(읽기 전용)
monofield rea apply … [--finding <id>…] [--write [--out <file>]]선택한 발견 사항을 명세서에 반영
monofield judge check --project <id> --input <spec>한글명·업무명 판단 검토(규칙 먼저, 모델은 선택)
monofield judge feedback|scorecard|policy|export검토 결과 라벨링·성적표·기준 적용·학습 데이터
monofield jev configure --backend local …로컬 판단 모델(Laya) 연결
monofield docs render-interface-spec --input <spec> --out <xlsx>인터페이스 명세서 → Excel
monofield docs preview-interface-spec | export-openapiHTML 미리보기 · OpenAPI 내보내기
monofield docs render-screen-spec --input <spec> --out <pptx>화면명세서 → PowerPoint

모든 명령은 --json 으로 기계가 읽는 출력을, --daemon-url 로 데몬 주소를 지정할 수 있습니다(render·preview 명령은 JSON 결과를 출력).

MethodPath설명
GET/api/projects/:id/browser-evidence기록 파일 목록
POST/api/projects/:id/browser-evidence/cross-check비교 (본문: inputFile, evidenceFiles)
POST/api/projects/:id/browser-evidence/apply반영 (findingIds, write, baseContentSha256 …)
POST/api/projects/:id/judgments/check판단 검토

데몬은 다른 웹 출처에서 온 요청을 거부합니다. 더 자세한 사용법은 REA·Laya 실전 가이드 와 판단 검토 문서 에 있습니다.

06

알아 둘 한계

  • "관찰되지 않음"은 "없음"이 아닙니다. 기록에 없는 필드는 그 시나리오에서 나타나지 않았을 뿐입니다. 응답 필드는 성공(2xx) 본문에서만 비교합니다.
  • 이 데모는 합성 데이터입니다. 고객 시스템에서 같은 결과가 나온다는 보증이 아닙니다.
  • 반영으로 추가된 행은 한글명이 비어 있고 필수 여부가 TBD입니다. 사람이 채우고 검토해야 하며, 기록된 응답 예시는 실제 데이터일 수 있어 기본으로 복사하지 않습니다.
  • 판단 모델의 답은 참고용입니다. 승인이나 배포 판단의 근거로 쓰지 않습니다.
  • Windows 데스크톱 프리뷰입니다. 코드 서명 전이고 기능은 바뀔 수 있습니다.
